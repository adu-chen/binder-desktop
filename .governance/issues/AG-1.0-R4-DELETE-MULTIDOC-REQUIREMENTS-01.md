# Issue Trace — AG-1.0-R4-DELETE-MULTIDOC-REQUIREMENTS-01：可恢复删除与多个既有文档独立编辑

文档状态：A
任务类型：DOC_ONLY
治理阶段：REQUIREMENT
创建时间：2026-08-14

## 1. 用户可见问题

文件/文件夹删除若在“接受 Proposal”时直接物理执行，就会绕开 LogicalState、显式保存和可恢复性；多个既有文档
若可被模型直接扩展目标或批量裁决，就无法让用户逐项掌握实际写入范围。两项都必须先收敛为可预览、可追溯、可失败
而不伪成功的 1.0 用户能力。

## 2. 已核实的实现漂移

- `ag_delete_proposal` 目前创建 `AG_DELETE` pending 卡，但 `route_apply_delete_diff` 在接受时直接调用删除；
  `delete_doc` 使用 `remove_file`，`delete_folder` 使用 `remove_dir_all`，没有可恢复存储。
- 文件树的手动删除也直接调用文件/目录删除，并关闭受影响标签，未先解决未保存 LogicalState。
- `guard_target_set` 对未知既有文档返回 `AcceptCrossDocument`，提示词也允许未声明既有文档成为 `cross_doc` 目标；
  当前没有已确认冻结的多目标计划，也没有逐目标授权约束。

上述为后续设计/迁移债务，不得用新增 Prompt 文案掩盖，也不能据此反向修改需求。

## 3. 本轮人类确认

1. 已保存文件/文件夹删除为 P1：先红色逻辑暂存与影响 Proposal，接受只裁决卡片，单项显式保存才移入可恢复存储。
2. 恢复同样先预览、后显式保存；永久删除不纳入 Agent 1.0。
3. 非空文件夹允许递归删除，但展示前冻结完整影响清单/数量，保存前重新核验来源与清单；范围变化则不执行。
4. 受影响未保存会话必须先保存，或用户明确关闭并丢弃；关闭标签不能静默丢失 LogicalState。
5. 多个既有文档编辑为 P1：先可见目标计划，用户确认后冻结成员、路径和身份；随后逐文档独立 Proposal、基准、预览、裁决、保存和失败。
6. M4 只限已保存 TXT、Markdown、HTML 与 BDocx 编辑副本；原生 DOCX、删除/文件树整理/格式转换混合操作排除。
7. 不提供批量接受、批量保存、跨文档全有或全无事务或动态追加目标。单目标冲突/外部变化/结构变化/删除只影响该目标。

## 4. 需求边界

- 删除的逻辑文件树暂存、显示状态与 DiskState 分离；删除/恢复的接受不是物理副作用。
- 新建未保存文档的拒绝/关闭仍属于 D-NEW 生命周期，不是磁盘删除。
- 多文档目标清单的引用身份或候选来源不构成写权限；只有用户确认后的冻结清单可被逐项 Proposal 消费。
- 每个目标继续遵循既有三分流：已有 LogicalState 时预览更新它、接受只裁决卡、保存才写盘；背景目标仅在自身卡接受时原子写盘，打开后迁移到前者。

## 5. 直接消费者

- ED：REQ-ED-015/016 承接删除前置的脏会话、标签处理和逐目标会话隔离。

## 6. 验收计划

- 删除文件、空文件夹和非空文件夹：检查红色预览、接受、显式保存、递归清单、再核验、失败和恢复。
- 受影响打开文档含未保存内容：验证保存/明确丢弃前阻断，且删除不以关闭标签静默丢内容。
- 删除保存后：验证标签、待审阅 Proposal、后续引用与已发送历史快照的差异；恢复冲突不自动覆盖。
- 多既有文档：验证目标计划确认/冻结、不同打开状态的三分流、逐目标卡片、逐目标保存、一项冲突或删除时其他项不受影响。
- 验证不出现原生 DOCX 写入、动态目标扩展、批量接受、批量保存或跨文档事务入口。

## 7. 待设计项

- 删除/恢复 Proposal、红色逻辑文件树、递归清单、脏会话和失效事件的共享对象/接口。

- 现有 `AG_DELETE` 接受即删除、文件树直接删除和 `remove_dir_all`/`remove_file` 违反本轮可恢复与显式保存边界。
- 现有 `AcceptCrossDocument` 和 Prompt 对未声明既有文档的宽授权违反目标计划确认/冻结边界。
- 迁移时不得通过隐藏按钮、弱化错误、吞掉删除失败或仅修改 Prompt 伪造符合基线；须在 DESIGN Scope 建立状态机、接口与验证后实施。
