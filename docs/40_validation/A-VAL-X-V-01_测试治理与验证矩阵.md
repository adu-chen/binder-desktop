# Binder 测试治理与验证矩阵

## 1. 目标与结论

Binder 的测试体系按“模块 × 测试深度 × 风险”治理：规则、链路和模块决定应测试什么；
变更文件决定本次触发什么；需求与验收标准决定产品最终验证什么。测试文件允许随功能动态变化，
但必须受 owner、layer、文件预算和失败关闭约束。

测试与验证不是互不相干的两套开发，也不应被做成不可回退的瀑布阶段：

- 自动化测试主要在 G2–G4 建立并随实现循环运行，证明技术约束与回归基线。
- 系统/需求验证主要在 G5–G6 聚合自动化证据并执行完整工作流、NFR 和发布环境检查。
- 验证发现缺陷时回到设计、实现或测试修复；不得用新增一个“能过”的测试替代需求闭环。

## 2. 权威源与持久化链路

| 内容 | 权威源 | 动态产物 |
|---|---|---|
| 测试治理通则、来源、层级、失败关闭 | ADU.md §5.6 | audit 规则 |
| 单次任务何时选择和执行测试 | ADP.md §5–§6 | Runtime Report `test_impact` |
| 项目阶段、风险与测试/验证边界 | APC §5、§10、§12 | G4/G5/G6 Gate 证据 |
| 模块路径、测试路径、风险、消费者、文件预算 | `.governance/test-governance.json` | related test plan |
| 当前测试文件、用例、layer、covers | 文件系统 + 测试源码 | ADUS 测试能力索引 |
| 需求完整验证 | REQ 与验收标准 | 验证记录、发布检查清单 |

注册表保存稳定关系，不保存容易过期的“完整测试文件列表”。`test:inventory` 每次从前端测试、
Rust 内联测试和 Rust 集成测试重新发现资产；`governance:generate` 将结果写入 ADUS 自动生成区。

## 3. 测试来源：如何确定该有哪些测试

每个计划项先形成行为清单，再选择最小可靠测试层：

1. RULE：主路径、边界值、拒绝条件、错误路径和不变量。
2. STATE_MACHINE：每个允许转移、禁止转移、终态幂等、恢复路径和并发/过期事件。
3. CHAIN / CONSTRAINT：跨模块输入输出、事件顺序、持久化、失败补偿和契约兼容。
4. 功能与组件：入口、用户动作、可观察状态、禁用/加载/失败/完成状态。
5. 缺陷：复现根因的最小回归测试，不能只断言补丁分支。
6. NFR：性能、安全、恢复、离线和发布环境中可自动度量的部分。

功能应在自动化可行范围内全覆盖，但“全覆盖”指可追踪的行为与风险闭合，不等于每行代码或每个 DOM
属性都写断言。未覆盖项必须分类为：`AUTOMATION_GAP`（应自动化）、`VALIDATION_ONLY`（目前只能
系统/人工验证）、`DEFERRED`（有阶段和退出条件）或 `OUT_OF_SCOPE`（有需求裁决）；不得无记录消失。

一个小按钮的单次交互通常在 component/state 层验证：触发事件后断言业务可观察状态、可访问属性或
命令调用；只有视觉质感、跨应用系统对话框、真实签名安装等无法稳定自动判断的内容才留给验证。

## 4. 深度与阶段矩阵

| 层级 | 主要对象 | 默认阶段 | 典型证据 |
|---|---|---|---|
| unit | 纯函数、解析、转换、边界计算 | G2–G4 | 输入输出、边界、错误 |
| state | store、状态机、选择器、不变量 | G2–G4 | 转移矩阵、终态、恢复 |
| service | I/O、Tauri command、编排、副作用 | G3–G4 | 调用契约、失败补偿、持久化 |
| component | 用户事件到可观察 UI 状态 | G4 | 点击/输入、状态、可访问语义 |
| integration | 跨模块、前后端、数据库、事件链 | G5 | CHAIN/CONSTRAINT、真实边界 |
| system | 完整需求路径、NFR、生产配置 | G5–G6 | 场景结果、性能、安全、恢复 |
| release validation | 安装、签名、公证、更新、生产门禁 | G6 | 发布清单和人类裁决 |

## 5. 当前健康基线（2026-08-01）

动态清单已识别 96 个测试资产、约 724 个测试用例：33 个前端测试文件、61 个 Rust 内联测试文件、
2 个 Rust 集成测试文件。97 个可执行源文件均有模块映射；当前无 unowned/unclassified 测试、无
`only`/`skip`/`#[ignore]`、无未知 `covers`。精确现状以 `npm run test:inventory` 为准。
规则注册表中 `BR-SYS-DATA-004` 属于客户端仓库外的云 provider catalog 契约，当前按既有
`CLIENT_OUT_OF_SCOPE_RULES` 裁决不计客户端缺测；云端实现进入对应 APC 时必须建立独立覆盖证据。

前端文件整合预算如下；Rust 内联测试继续与实现同文件，不计入“模块少量文件”目标：

| CORE | high | 1 | 1 | 达标 |
| SYS | critical | 3 | 3 | 已于 TEST-CONSOLIDATION-SYS-01 达标；52 个 owner 用例保持 |
| WS | critical | 6 | 2 | 待整合 |
| ED | critical | 7 | 7 | 已于 TEST-CONSOLIDATION-ED-01 达标；207 个 owner 用例保持 |
| DE | critical | 4 | 2 | 待整合 |
| AG | critical | 8 | 3 | 待整合 |
| DOC | critical | 1 | 1 | 达标 |

现状的关键问题不是测试不存在，而是除 ED、SYS 外的前端文件仍有碎片化、部分模块靠同一测试跨模块关联，
以及 G5/G6 系统验证记录尚未形成统一台账。ED 与 SYS 已分别按 7 个和 3 个真实物理套件完成整合，
没有使用 helper/case 文件隐藏测试；其余模块继续按独立 Scope 合并。

## 6. 目标套件大纲

物理文件以可诊断性为准，不强制所有内容塞进一个文件。建议后续按以下逻辑套件整合：

- SYS（3，已落地）：ShellComponents；systemRuntime；systemState。
- WS（≤2）：workspace UI/store；workspace I/O、timeline、恢复与集成。
- ED（≤7）：editor core；文档格式与 codec；分页/viewport；结构移动与表格/图片；
  service/persistence；store/outline/view preferences；component interaction。
- DE（≤2）：Diff Edit UI/store；生命周期、持久化与集成。
- AG（≤3）：代理 UI；session/runtime/service/store；assist/selection/placement。
- DOC / PRV / REF（各≤1）：按模块服务与契约聚合。
- Rust：纯单元测试保留内联；只有跨模块真实边界放入少量 `src-tauri/tests/*.rs` 集成套件。

每次合并必须保持用例语义、断言强度和 `covers`，先运行旧/新套件对照，再删除空壳文件；不得以达成
文件数为由删除低频边界、失败路径或状态转移测试。

## 7. 变更触发算法

1. 输入本次实际 changed files。
2. 直接测试变更：直选该测试，不推断业务源变化。
3. 业务源变更：根据路径、规则引用与 @GOV 映射直接模块。
4. critical/high 风险：加入一跳直接消费者；不递归无限放大。
5. 共享前端配置或广泛模块影响：前端全量。
6. Rust/Cargo 或要求跨层回归的高风险模块：Rust 全量。
7. TypeScript 业务源：附加类型检查。
8. 非测试变化：附加治理审计。
9. 任一可执行文件无模块映射：失败关闭，先补登记或静态定义。

该算法保证“准确触发”是可解释和保守的：不会承诺语义上绝对零漏测，但会输出文件→模块→消费者→
命令的完整计划，遇到未知项阻断而不是猜测。动态需求通过更新设计/路径注册和真实文件清单自然进入下一次计算。

## 8. AI coding 操作协议

对编程基础薄弱的使用者只要求描述目标并确认 Scope；AI 承担映射和命令选择：

```bash
npm run test:inventory
npm run test:plan -- --files <本次变更文件...>
npm run test:related -- --files <同一组变更文件...>
```

AI 必须把计划中的直接模块、影响模块、定向/全量升级和实际结果写入 Runtime Report。测试失败时说明
失败行为和根因，不要求使用者理解测试框架术语；验证阶段则用需求语言展示“场景、预期、实际、证据、
未验证项”。这使 vibe coding 的交互保持简单，同时工程门禁不依赖用户手工挑测试。

## 9. 验证方案

每个进入 G5 的需求按 REQ 形成场景卡：前置条件、完整操作、期望结果、自动化证据、人工观察项、
环境、实际结果、缺陷链接和裁决。原则是能自动则自动；人工部分单独列出，不混入测试通过率。

Binder 当前优先验证域：

- 核心编辑闭环：打开/编辑/保存/重载，Markdown/HTML/DOCX 与媒体引用保持。
- 代理编辑与 Diff Edit：工具调用、预览、接受/拒绝、过期、落盘、失败恢复。
- workspace 生命周期：创建/切换/关闭、未保存保护、timeline、重启恢复。
- 构建与 AI 门禁：构建中断/移交、模型调用、认证订阅和网关契约。
- 发布与 NFR：大文档性能、离线边界、数据库迁移、崩溃恢复、DMG 签名公证与更新。

自动化证据不足的功能不得表述为“验证通过”。可在当前阶段延期，但必须记录责任模块、目标阶段和
退出条件；进入 G6 时，发布范围内的 REQ 不能保留无裁决的 `AUTOMATION_GAP` 或 `VALIDATION_ONLY`。

## 10. 治理验收与后续 Scope

TEST-GOVERNANCE-01 的验收是能力闭环，不是一次性整理全部测试文件：

- 注册表、动态清单、影响选择器与自测存在且 audit 硬接线。
- ADUS 能生成真实测试覆盖和能力索引。
- CODE_CHANGE / MINOR / TEST_ONLY 有统一执行入口和 Runtime Report 证据。
- 当前文件增长被冻结，六个模块的整合债务可量化。
- 测试与需求验证各自有权威来源和交付证据。

后续应按模块分别开 Scope，从 WS 开始继续合并测试套件；另开 VALIDATION Scope 建立核心编辑、代理编辑、
workspace 恢复与发布验证场景卡。两类工作不应混在本治理基础设施改动中。
